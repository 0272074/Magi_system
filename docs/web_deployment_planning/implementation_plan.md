# Web公開・マルチユーザー化に向けた実装計画

本アプリをWeb公開し、「ユーザー自身のAPIキー利用（BYOK）」「Google SSOによるログイン」「チャット履歴の保存」を実現するためのアーキテクチャ改修計画です。

## ユーザー確認事項 (Open Questions)

この計画を進めるにあたり、いくつか重要な設計判断があります。以下の選択肢からご希望をお知らせください。

> [!IMPORTANT]
> **1. APIキーの保存・管理方法**
> * **[推奨] A. ブラウザ保存 (Local Storage):** ユーザーが入力したキーをブラウザにのみ保存し、リクエストの都度バックエンドへ送信します。サーバー側に他人のAPIキーを保存しないため、セキュリティリスク・管理責任を大幅に減らせます。
> * **B. サーバーDB保存:** ユーザーのアカウントに紐付けてサーバーのDBに暗号化して保存します。どの端末からログインしてもすぐに使えますが、暗号化の実装や漏洩リスクの管理が必要です。

> [!IMPORTANT]
> **2. 認証 (SSO) とデータベースの技術選定**
> * **[推奨] A. Supabase (BaaS):** 認証（Google SSO等）とデータベース（PostgreSQL）をセットで提供するサービス。認証の実装が極めて容易で、本番環境への移行もスムーズです。
> * **B. Firebase Auth + サーバーサイドDB:** 認証のみFirebaseを利用し、履歴等のデータはFastAPI側のDB（SQLite等）に保存します。
> * **C. フルスクラッチ (FastAPI + Authlib + SQLite):** 外部のBaaSに依存せず、FastAPI上でGoogle OAuthを実装し、自前のデータベースで管理します。

> [!TIP]
> **3. フロントエンドのフレームワークについて**
> 現在は素のJavaScript (Vanilla JS) を使用していますが、認証や履歴表示などの状態管理が増えるとコードが複雑になります。このタイミングで **React (Vite等)** などを導入するか、引き続き Vanilla JS で進めるかご希望はありますか？

## 提案する実装ステップ（推奨案の場合）

### Phase 1: APIキーのユーザー設定化 (BYOK)
サーバーの `.env` 依存から脱却し、ユーザーがキーを入力できる仕組みを作ります。
1. **Frontend:** 
   - 画面に「⚙️ 設定」ボタンとモーダルを追加。
   - Gemini, Groq, OpenRouter の各APIキーを入力・保存（`localStorage`）するUIを作成。
   - APIリクエスト（`/api/council`）送信時に、これらのキーをリクエストデータ（JSON）に含めて送信するよう修正。
2. **Backend:**
   - `CouncilRequest` スキーマを拡張し、APIキーを受け取るように変更。
   - 各AI呼び出し関数（`get_gemini_answer` 等）で、環境変数ではなく受け取ったAPIキーを使用するように修正。

### Phase 2: 認証とデータベース (Supabase等を想定)
1. **Backend:**
   - SQLAlchemy 等を使用し、DBモデル（`User`, `Session`, `Message`）を定義。
   - 認証トークン（JWT等）を検証するミドルウェア / 依存関係を追加。
2. **Frontend:**
   - ログイン画面 / Googleでログイン ボタンの実装。
   - ログイン成功後、APIリクエストに認証トークンを付与。

### Phase 3: チャット履歴の保存と読み込み
1. **Backend:**
   - 履歴を保存するAPI (`POST /api/history`) と取得するAPI (`GET /api/history`) を実装。
   - 議長AIの完了時（`COMPLETE`）に、DBへ合議結果を自動保存するロジックの追加。
2. **Frontend:**
   - 画面左側等にサイドバーを追加し、過去のチャット履歴（セッション一覧）を表示。
   - 履歴をクリックした際、過去の回答結果画面を復元して表示する機能の実装。
